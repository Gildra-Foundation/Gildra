# Build-pinned auction enhancement subset

Generated by `python3 apps/web/scripts/build-auction-enhancement-catalog.py` from the existing local catalog using **read-only SQL transactions** and the exact SimulationCraft revision pinned by the project. No imports, migrations, services or purchases. `catalog.json` includes original DB2 row payloads, source artifact UUIDs, build, native source URL/hash, and deterministic SHA256 revision. The generator reverse-maps every pinned permanent enchant rule through its direct application spells. It searches every prismatic GemProperties row across expansions and every later quality mapping for a native enchant. Checked-in profession outputs provide additional source records. The native permanent enchant table supplies exact equipment applicability and ranks.

The source contains 303 tradeable prismatic gems, 682 direct effect-53 consumables and 391 verified ranked effect-301 mappings. The native simulator receives gem item IDs and permanent enchant IDs. For example, armor kit 244643 applies enchant 8163 (rank 2). Gem 240967 has property 4408, effect 8556 and category 698 with a shared limit of one.

Of the 1,376 mapped consumables, 48 have an additional spell effect and one has an unsupported condition; 1,327 reach character and equipment checks. The snapshot contains 1,043 distinct native enchant IDs. Of these, 38 have no purchasable mapping and 49 have only restricted mappings. Of 394 later quality rows, 392 passed parity. Item 225652 is bind-on-pickup; quality rows 327 and 328 for items 223664 and 223665 failed the full-chain comparison. Their separate source rows 194 and 195 passed for crafting data ID 1581.

Ranked mappings have an explicitly separate pinned source build **12.1.5.70783**, from the existing catalog's CraftingDataEnchantQuality. Engine/rules remain **12.1.0.69587**. The generator requires payload parity for the complete Item, ItemSparse, ItemXItemEffect, ItemEffect, SpellEffect, SpellEquippedItems, CraftingData and SpellItemEnchantment chain, and Item.CraftingQualityID must equal the quality row Rank. Every existing field must match; the only tolerated schema addition is explicit SpellItemEnchantment.ItemSquishEraID=0. Missing fields, other additions, changed conditions/stats/levels, missing/ambiguous chains fail closed. Each compatibility proof stores source artifact UUIDs and source-payload hashes. This is evidence of engine-chain compatibility with an authoritative later mapping, **not** a claim that the missing historical mapping table was recovered. Native exact enchant ID + equipment masks supply the displayed rank. No names or adjacent IDs participate.

Semantic closure is compared separately for every mapped item: both builds query **all** ItemXItemEffect rows by ItemID, fetch all their referenced ItemEffect records, then query **all** SpellEffect and SpellEquippedItems rows by the resulting SpellIDs. Equality requires identical `(table,row ID,payload)` sets, including non-applying/secondary effects. New links, extra effects, extra equipped-item restrictions, deleted rows or changed payloads reject that mapping. Later relationship queries are never restricted to old relationship row IDs. Proofs include `semanticRowsetVersion=1` and complete per-table row ID sets; the resolver rejects proofs without that version. This applies a **newer-source mapping to compatible pinned native effects**; it does not prove what the absent historical CraftingDataEnchantQuality table contained.

Real ranked example: Item 244010 → ItemXItemEffect 142170 → ItemEffect 211201 → spell 1236086 → SpellEffect 1231783 (type 301, CraftingData 3827) → source quality row 479 (ItemID 244010, Rank 13, enchant 8020); native rules identify rank 1. Row 480 independently maps item 244011, quality 14, enchant 8021/rank 2. Records expose `mappingBuild`; catalog info exposes `rankedMappingSourceBuild`. Snapshot schema version is now 2.

`auctionEnhancementCatalog.ts` exports:

- `auctionEnhancementCatalogInfo`: version, build, revision (data SHA256), simcRevision, completeness, coverage, missing.
- `auctionEnhancementRecords`, `auctionEnhancementConsumableIds`: exact data subset; consumers must use the resolver to filter restrictions.
- `resolveExactEnhancements(target, character)`: target `{itemId, inventoryType, itemClassId, itemSubclassId, itemLevel, socketColors:[number,number,number], engine, build, revision, hasOnUseEffect?}`. Target revision means **simcRevision**, not catalog revision. Character `{level, faction?, professions?}`; professions may be the exact skill/rank array or a character profession snapshot. Returns `{verified:false,reason}` or `{verified:true,enchantApplicable,enchantChoices,gemChoices,coverageGaps?}`. Keys of gemChoices are native socket indexes `"0".."2"`; root maps them to its exact socket keys. Only ordinary prismatic socket/color 14 is supported. All three native socket positions must be supplied, including zeros.
- `lookupInstalled(kind, simulationId)`: returns `{verified:true,enhancement}` or `{verified:false,reason}`. For retained native permanent enchants without a purchased mapping, consumableItemId is **0**, never a purchasable choice. Unknown installed gems remain unknown rather than losing category constraints.

Records carry equipment class, inventory/subclass masks, item-level bounds, required character level, faction, profession, native rank, raw crafting quality ID and source row references. Search enforces the independent unique-equipped and shared gem-category limits across retained and purchased gems. A consumed scroll requires a single linked on-use ItemEffect with a single charge and a single applying effect. A formula, soulbound item, ambiguous chain, conditional rule or additional spell effect cannot supply a purchase choice. The resolver enforces the consumable's RequiredLevel and the enchant's ItemLevelMin/ItemLevelMax. SimC uses SpellItemEnchantment.MinLevel/MaxLevel as scaling fields. [Pinned SimC structure](https://github.com/simulationcraft/simc/blob/18428cd3902412abc8ee274d19567d603e674e66/engine/dbc/spell_item_enchantment.hpp)

An engineering enchant with a use spell also requires a target free of another use effect. A verified exact variant with an explicitly empty effects array or an owned item with an explicitly empty spells array satisfies this requirement. Other target effect metadata yields `target_effects_unverified` and leaves other choices available. Unknown skill or faction yields its own coverage gap for otherwise possible enhancements. [Item enchant use-effect checks](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/game/Spells/Spell.cpp#L7075-L7086)

Purchasable records also expose `name` directly from verified `ItemSparse.Display_lang` (source locale `en_US`), suitable as an EN fallback in either UI locale. No translated or ID-derived name is invented. `name` is optional on the shared record type because installed-only native records have no consumable item name.

An applicable enchant with no supported scroll has `enchantApplicable=true`, an empty choice list, and the coverage gap `no_supported_enchant`. A verified prismatic socket with no supported gem similarly has an empty list at its own index and the gap `no_supported_gem`. Exact search can still price the bare item and other verified improvements. These gaps prevent a fully enhanced claim. A genuinely inapplicable enchant has `enchantApplicable=false`. Unknown target metadata or native applicability still fails verification. Ring/head/chest now have real ranked choices. A reverse ID traversal of uncapped native wrist rules additionally found 5 purchasable mappings for Swift/Safe/Cooled/Shaded Hearthing. These are utility enhancements, **not evidence of DPS gain**. Native stat-wrist rules capped at item level 120/170 remain excluded above that level; do not promise modern wrist combat benefits from these utility records.

Eversong examples from the 18 November capture include Heavy Mithril Shoulder (7918, item level 13), ring 20818 (level 11), and necklace 20950 (level 12). Pinned direct spell applications link Borean Armor Kit 38375 to enchant 3329, scroll 110617 to ring enchant 5284, and scroll 110624 to neck enchant 5285. The generator includes tradeable consumables (Item.ClassID 0 or 8, Bonding 0, 2 or 3); a positive auction listing is still required for purchase. Low-level prismatic sockets can use Void Sphere 22459 and Prismatic Sphere 22460. They share enchant 5233, retain distinct item IDs and receive independent quotes. Steel Weapon Chain 6041 applies enchant 37 to a compatible weapon up through item level 80. Crude Scope 4405 comes from historical consumable class 0, and Pyrium Weapon Chain 55057 is bind-on-equip. Ring 20906 at level 8 and neck 258911 at 159 have no matching native enchant. A high-level waist can accept a compatible engineering modification when the character and target meet its requirements. Missing native level bounds yield `enchant_applicability_unknown`.

The saved Eversong 16-slot, 500-gold search contained 1,284 candidate/slot rows. With level 90, Horde, an empty profession list and the captured commodity prices, 1,252 had an eligible enchant choice (previously 910); 1,208 had an item and at least one compatible scroll jointly within budget (previously 884). The union required 1,116 distinct consumable quotes, with 1,064 listed. The largest individual choices were 162 enchant consumables and 302 gem consumables. These counts replay the captured eligibility and auction prices and do not measure combat performance.

Remaining: historical CraftingDataEnchantQuality for engine build 92 is still absent (no matching source artifact); public `https://wago.tools/db2/CraftingDataEnchantQuality/csv?build=12.1.0.69587` returned 403 in the prior source check. Local builds 180/1608 hold the table; only build 1608 is used for the explicit later-mapping compatibility layer. Effect 288 recipes and conditional/special sockets are not resolved. Source tables contain ItemLimitCategory and explicit LimitCategory=0, so ordinary gems no longer have unknown category. Supported nonzero categories require flags=1 and a positive base quantity; conditional enhancements fail closed. Coverage is a subset and must remain visible in result metadata.
