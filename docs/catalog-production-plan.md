# Warcraft catalog: production completion plan

## Цель

Собрать полезную и проверяемую библиотеку Warcraft в `api.gildra.net`: единый каталог предметов, заклинаний, существ/NPC, заданий, рецептов, наград, валют, маунтов, игрушек, достижений, карт и игровых медиа. Статистика тир-листов остаётся отдельными датасетами и не смешивается с фундаментом игровых данных.

## Команда и зоны ответственности

| Роль | Ответственность | Готовый результат |
|---|---|---|
| Импорт и обогащение | Blizzard API, Wago.Tools/DB2, CASC и wow-listfile; повторяемый импорт, локализации, media | Полные candidate-снимки и отчёт покрытия |
| Целостность и релизы | схемы, связи, provenance, quality-gate, миграции, rollback | Атомарный release или сохранённый предыдущий release |
| API и библиотека | REST/GraphQL, поиск, фильтры, карточки, tooltip, изображения, EN/RU | Страница Library и стабильный контракт API |
| Релиз и эксплуатация | локальные backup/restore-дриллы, CI, health-check, деплой, журналирование | Проверенный production-релиз на OVH за Cloudflare |

Работа выполняется параллельно, но публикация разрешается только после прохождения всех проверок целостности. Sentry пока не включается; для диагностики используются структурированные логи, метрики pipeline и audit-отчёты.

## Источники и правила использования

1. **Blizzard API** — официальный источник деталей, названий, описаний, локализаций и ссылок на media. Он не заменяет DB2 и не содержит всех отношений игры.
2. **Wago.Tools/DB2** — структурированные таблицы предметов, заклинаний, эффектов, рецептов, заданий, NPC, карт и вариантов по build.
3. **CASC + wow-listfile** — подтверждение файлов клиента и получение иконок/asset-идентификаторов.
4. У каждой строки сохраняются источник, build, URL/файл, hash и время получения. Нельзя выдавать fallback как настоящий перевод и нельзя вычислять неизвестные spell variables догадками.
5. Текущий режим публикации закрытый: внутренние источники можно использовать для нашей панели, но перевод в публичный API выполняется только после отдельного подтверждения прав на каждый источник.

## Этапы

### 1. Каноническая модель и инвентаризация

- Зафиксировать product/expansion/build и единый identity ключ сущности.
- Разделить `raw → normalized → version → localization → relationship → media → release`.
- Составить coverage-матрицу по retail, Classic, Classic Era и Hardcore.
- Добавить обязательное состояние `missing`, чтобы отсутствие данных было видимым, а не превращалось в пустую карточку.

**Выход:** миграции и схема, на которой можно безопасно повторять импорт.

### 2. Полный источник DB2/Wago

- Импортировать все доступные таблицы по каждому продукту и build.
- Обеспечить cursor/batch обработку, checkpoint и идемпотентные upsert-операции.
- Не активировать более старый build поверх нового.
- Пересобрать предметы, варианты и эффекты, заклинания и эффекты, рецепты и реагенты, задания и награды, NPC и карты.

**Выход:** candidate-снимок без потери строк относительно предыдущего build.

### 3. Официальные детали и локализации

- Для item/spell/creature выполнить detail-запросы Blizzard, а не только search payload.
- Сохранить EN и RU отдельно, включая raw/resolved description.
- Неразрешённые `$s`, `$d`, `$@spelldesc` хранить как явные токены с диагностикой.
- Не считать английский fallback русским переводом.

**Выход:** карточка показывает, что действительно пришло из источника и что ещё отсутствует.

### 4. Медиа и картинки

- Нормализовать icon/media identity в универсальную таблицу media.
- Сопоставить DB2/CASC icon-файлы, Blizzard media URL и локальный cache.
- Проверять MIME, размер, checksum и HTTP-код; 403/404 не должны ломать весь импорт.
- В UI показывать реальную картинку, а при отсутствии — честный placeholder с причиной.

**Выход:** tooltip и detail-страницы имеют изображения для всех сущностей, для которых источник их предоставляет.

### 5. Связи и игровые источники

- Заполнить способы получения предметов: квест, продавец, NPC, босс, профессия, достижение, валютный обмен.
- Подтвердить цепочки `NPC → loot → item` с build/difficulty/chance.
- Привязать рецепты к реагентам и результатам, задания к objectives/rewards.
- Исправить семантику карт: ATT map IDs трактуются как UiMap, а DB2 Map остаётся отдельным типом.

**Выход:** на карточке предмета видны источники, а на карточке NPC — роли, места и loot.

### 6. Classic-линейки

- Отдельно импортировать Classic, Classic Era и Hardcore.
- Проверить, что retail-identity не пересекается с классическими версиями без product/build.
- Заполнить quests, creatures, spells, items, recipes, maps и localized strings.

**Выход:** четыре продукта отображаются в одном каталоге без подмены данных.

### 7. Качество и доказуемость

- Проверять orphan-ссылки, дубли identity, отсутствующие версии, invalid constraints и build regression.
- Для каждой опубликованной строки требовать source artifact и provenance.
- Критические регрессии блокируют публикацию; media и необязательный перевод дают предупреждение, а не скрытую потерю.
- Формировать JSON/табличный audit-отчёт на каждый pipeline run.

**Минимум перед публикацией:** candidate validated, не хуже предыдущего по именам/описаниям/структурным фактам, нет критических orphan-связей и есть проверенный backup.

### 8. API и публичная библиотека

- REST и GraphQL отдают полную сущность, версии, локализации, description blocks, tooltip, media, relations, quality и provenance.
- Library: список датасетов → фильтры → карточка сущности → связанные сущности.
- EN/RU переключаются независимо; поиск и пагинация используют read models.
- Tooltip содержит имя, тип, icon, краткое описание и ссылку на подробную карточку.
- Для приватного режима сохраняется admin session; публичный режим включается только после разрешений источников.

### 9. Резервирование и отказоустойчивость

- Перед каждым production import делать локальный зашифрованный dump.
- После dump выполнять автоматическое тестовое восстановление и сравнивать контрольные числа.
- При ошибке импорта не менять current published pointers.
- Хранить несколько последних локальных архивов и журнал manifest/signature.

### 10. CI/CD и выпуск

- CI: миграции, Go unit/race tests, Testcontainers integration tests, TypeScript typecheck, OpenAPI/GraphQL generation, lint и image build.
- Candidate image публиковать по digest; production deploy только digest-pinned образом.
- После deploy выполнить health, private-library, API contract и catalog-audit проверки.
- Выпускать небольшими атомарными релизами: сначала данные и API, затем UI; rollback возвращает прежний release pointer.

## Текущий порядок выполнения

1. Дождаться полного retail foundation pipeline, запущенного с unbounded import и recovery gate.
2. Снять coverage/orphan/provenance отчёт и сравнить его с последним опубликованным snapshot.
3. Исправить найденные блокирующие связи (в первую очередь UiMap, recipe item links и отсутствующие source grants для public режима).
4. Выполнить отдельные Classic/Era/Hardcore импорты и повторить quality-gate.
5. Собрать digest-pinned API/web images, прогнать CI и развернуть закрытый production release.
6. Проверить `api.gildra.net/ru/library` и `/en/library`, карточки item/spell/creature/quest, tooltip и media.
7. После накопления доказательств по лицензиям отдельно решить, какие поля можно открыть публично.

## Критерий готовности

База считается production-ready не по числу строк, а когда каждый опубликованный объект имеет каноническую identity, build, источник, доступные локализации, проверенную структуру, видимый статус полноты и корректную карточку в Library; при неудаче нового импорта пользователь продолжает видеть последний проверенный release.
