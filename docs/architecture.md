# Gildra architecture

Go backend domains, their dependency rules and the test that enforces them: [backend-domains.md](backend-domains.md).

Gildra is deployed as one modular monolith: one repository and one OVHcloud deployment, with isolated processes for the public site, API/worker and CMS.

```text
Visitors -> Cloudflare -> nginx on OVHcloud
                         |-- gildra.net ------> Next.js web
                         |-- gildra.net/api --> Go API + River workers
                         `-- cms.gildra.net --> Payload CMS

Sources -> Go importers + Python scrapers -> PostgreSQL catalog

Go API -> PostgreSQL (catalog, users, subscriptions, River jobs)
       -> ClickHouse (product analytics)
       -> Redis (short-lived analytics cache)
```

## Repository layout (roadmap item 81)

One repository, npm workspaces for the JavaScript side:

| Path | What | Build |
| --- | --- | --- |
| `apps/web/` | public Next.js site (`@gildra/web`) | root `Dockerfile` (context = repo root; the runner flattens the standalone output to `/app/server.js`) |
| `packages/atlas-ui/` | atlas kit (`@gildra/atlas-ui`, TS source, no app imports) | transpiled by the site (`transpilePackages`) |
| `packages/game-data/` | game data + content manifest (`@gildra/game-data`) | same |
| `backend/` | Go API, River workers, importers, migrations | `backend/Dockerfile` |
| `cms/` | Payload CMS (own lockfile) | `cms/Dockerfile` |
| `scraper/` | Python scrapers | `scraper/Dockerfile` |
| `infra/`, `deploy/`, `compose*.yml` | host deployment | — |

`npm ci` at the root installs the workspaces; every web script runs from the
root (`npm run build` → `npm run build -w @gildra/web`). Paths in the sections
below are relative to `apps/web/`.

## Web front end: one page architecture

Every public page is built the same way (roadmap items 71–80):

- **Feature module** — `components/wow/<feature>/` with a public `index.ts`, a
  page component that takes `locale: "en" | "ru"`, its `*Copy.ts` (same keys in
  both languages, checked by `npm run test:atlas`) and a CSS module on `--atlas-*`
  tokens (`npm run atlas:check`). `npm run new:feature` copies the template
  (`components/wow/_template`, README there). Features never import another
  feature's insides — shared pieces live in `components/wow/shared`, the kit in
  `components/atlas` (ESLint `no-restricted-imports`).
- **Routes** — `app/(site)/<path>/page.tsx` and its `app/ru/<path>/page.tsx` mirror are
  thin wrappers (`npm run new:page`); the two trees are the two root layouts, so the
  server sends the right `<html lang>`. An English page that starts with the
  `// routes:mirror` line gets its `/ru` twin generated by swapping the locale
  (`npm run routes:mirror`); section pages take their metadata from
  `lib/routes/metadata.ts` (canonical and hreflang from the registry path).
  `npm run routes:check` keeps every page and link preview paired and the
  generated mirrors fresh. Link previews: `npm run new:og`.
- **Sections** — `lib/routes/registry.ts` holds every section's path, parent and
  short name; breadcrumbs come from `trail(locale, section, …)` and the quick
  search lists the same sections. Scenes (art, crop, tint, sparks) come from
  `lib/atlas/scenes.ts`.
- **Data** — game data reaches components only through `@/lib/data/wow`
  (server-only); ESLint forbids `@/data/*` outside `lib/`. Feature switches live
  in `lib/flags.ts`.

Two deliberate exceptions keep their own shape: **block pages** (`definePage` in
`lib/games/<slug>/pages`, CMS can override their block list — `/tier-lists`,
`/privacy`, League of Legends) and **workbenches** (database, search, API
console, rotation lab), which are client-heavy tools on the same kit and tokens.

### CMS boundary and block contracts (roadmap item 85)

The CMS (Payload, `cms/`) owns editorial content only: articles, readers, site
design previews and, for block pages, the *order and props* of blocks in a
page's `blocks` JSON. Everything else — block code, data loading, routes,
game data — stays in the web app. The contract between the two is
`contracts/blocks.schema.json`: the JSON Schema of every block's props,
generated from the block types (`npm run blocks:contracts`, checked for
freshness in CI). The web app accepts a CMS override only if every block's
type exists and its props match the contract (`lib/blocks/contracts.ts` in
`lib/cms/pages.ts`); anything else falls back to the TypeScript page, so an
editor's typo never breaks a page. The CMS can validate the same file before
publishing.

## Ownership

- `app`, `components`, `lib`: Next.js 16 public website, Tailwind CSS, shadcn/ui, next-intl and Recharts.
- `components/database`: focused catalog tooltip and relationship presentation;
  the page directory itself stays responsible for search and navigation.
- `backend`: Go 1.26 API generated from `backend/api/openapi.yaml` with oapi-codegen.
- `backend/internal/catalog`: public catalog read model, split by entities,
  ownership, mentions and relationship traversal.
- `backend/migrations/postgres`: Goose migrations for the versioned catalog,
  source provenance, relationship graph, users, subscriptions and River jobs.
- `backend/migrations/clickhouse`: Goose migrations for event storage and hourly aggregate materialized views.
- `cms`: Payload CMS with localized pages and guides, media and draft publishing.
- `compose.yml`: local/full stack.
- `compose.prod.yml`: OVHcloud origin TLS and immutable GHCR images.

The TypeScript API types and Go server types are generated from the same OpenAPI document. `oapi-codegen` generates Go; `openapi-typescript` generates TypeScript because oapi-codegen itself is Go-specific.

## Data model

PostgreSQL is the source of truth for versioned catalog entities, normalized
facts and relationships, source documents, publication state, accounts,
subscriptions and durable River jobs. Quest rewards are stored as catalog
entities and linked through normalized `rewards` relationships, so the same
data powers tooltip cards and graph navigation. Payload uses a separate
`gildra_cms` database on the same PostgreSQL instance, so its schema lifecycle
cannot collide with application migrations.

ClickHouse stores append-only events in monthly partitions with a 13-month TTL. Its ordering key is optimized for overview queries, and an incremental materialized view maintains hourly event and visitor states. Redis caches overview responses briefly and is never a source of truth.

For local Windows development, `compose.local.yml` exposes ClickHouse only on
loopback and keeps its persisted volume while running the container with a
read-only root filesystem. Docker Desktop requires CPU virtualization to be
enabled in firmware (AMD SVM/AMD-V or Intel VT-x); when it is disabled, the
catalog can still use PostgreSQL but `/readyz` and analytics remain degraded.
After virtualization is enabled, start the local dependency with:

```powershell
docker compose -f compose.yml -f compose.runtime.yml -f compose.local.yml up -d clickhouse
```

## Operations

- `/livez` checks the Go process.
- `/readyz` checks PostgreSQL, ClickHouse and Redis.
- Sentry is initialized in Next.js and Go when a DSN is provided.
- IndexNow submissions are validated for `gildra.net`, persisted as River jobs and retried up to eight times.
- CI regenerates contracts, validates Goose migrations, runs Go race tests, builds both Next.js apps and starts real PostgreSQL and ClickHouse instances through Testcontainers.
