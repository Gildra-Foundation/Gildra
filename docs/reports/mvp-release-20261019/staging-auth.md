# Battle.net: оставшаяся приёмка на staging

MVP развёрнут в отдельном проекте `gildra-staging` через `infra/staging/compose.mvp.yml`. Web и реальные обработчики metadata/workspace используют отдельную PostgreSQL; публичный каталог доступен через GET/HEAD allowlist без cookies и Authorization. Реальный OAuth ещё не проверен.

## Подключение Battle.net владельцем

- Публичный адрес: `https://staging.gildra.net`; результаты внешней проверки — в `staging/REPORT.md`.
- В production уже присутствуют Client ID/Client Secret (проверено только наличие, значения не выводились). Самый короткий путь: владелец добавляет **дополнительный** Redirect URI `https://staging.gildra.net/api/auth/callback/battlenet` в существующее приложение Gildra, сохраняя callback основного сайта. После подтверждения можно безопасно подключить те же серверные ключи к staging. Сейчас они не скопированы и вход выключен.
- Альтернатива, если владелец предпочитает отдельное приложение: создать Gildra Staging и внести его ключи через `sudoedit /opt/gildra-staging/auth.env`. Секреты в чат не отправлять.
- Серверные переменные: `AUTH_URL=https://staging.gildra.net`, собственный `AUTH_SECRET`, `BATTLENET_CLIENT_ID`, `BATTLENET_CLIENT_SECRET`, `BATTLENET_REGION=eu`.
- Запрашиваемые права: `openid wow.profile`. Код использует state, PKCE и nonce.
- Собственный `AUTH_SECRET` staging уже сгенерирован в `/opt/gildra-staging/auth.env` (root, 0600); Client ID/Secret пока пустые. Production cookies и AUTH_SECRET не копировать. Секреты не записывать в репозиторий, URL, отчёт или чат.
- Сохранить `GILDRA_STAGING=1`, noindex и отключённую аналитику. Вход должен возвращаться на тот же HTTPS origin; обратный прокси должен передавать верные Host/protocol.

## Изоляция данных и порядок

1. Владелец подтверждает добавленный callback и регион (по умолчанию EU). Пароль и одноразовые коды вводит сам на Battle.net. Для другого варианта — отдельное приложение, как описано выше.
2. Выполнено: candidate web + staging command, использующий текущие настоящие Go handlers. Изолированная БД содержит исходные миграции metadata и workspace 00004/5/6/10/14/170/171; прочие production подсистемы и фоновые задания не запускаются. Записи workspace остаются в staging. Точная ведомость — `staging/migrations.json`.
3. Выполнено: `verified-tier-candidate.json` опубликован штатным атомарным publisher только в staging, 80 записей/40 специализаций/6 сочетаний. Исходные времена получения 19 октября 11:02 UTC сохранены; дата не выдается за время нового получения. Для production нужен свежий сбор.
4. Подключить зарегистрированные staging credentials и проверить callback. Не переносить секреты в клиентский JavaScript. Новый GET/POST `/api/auth/session` возвращает только стандартные публичные поля с private/no-store.
5. В браузере владельца: вход → EU → список персонажей → профиль → смена региона → таланты → создание/переименование/обновление/загрузка/удаление → выход → повторный вход. Зафиксировать частичный ответ региона, закрытый профиль и истёкшую сессию.
6. Второе реальное устройство: прочитать билд, вызвать конфликт правок, проверить удаление; отдельный аккаунт не должен видеть исходную библиотеку. Публичную ссылку открыть в чистом браузере без входа.
7. Сохранить результат и скриншоты без account ID, токенов и персональных данных. Только после этого закрыть OAuth/staging критерий.

## Что уже проверено

Браузерные сценарии настоящего компонента `CharacterTalentBuilds` с реальным деревом талантов и изолированным тестовым workspace transport прошли на двух browser contexts. SQL/HTTP тесты проверяют серверные revisions, tombstones, лимит и владельца. Эти результаты дополняют, но не заменяют вход в Battle.net на staging.

В этой задаче опубликован только staging. Production приложение и боевые рейтинги нами не обновлялись; резервная копия и восстановление проверены для новой staging БД. Перед отдельной командой на выпуск нужны свежая успешная резервная копия и проверка восстановления: прежний catalog backup отмечался как неуспешный.
