## Что собирается

Два ограниченных GET: `/api/v1/raiding/static-data?expansion_id=11` и `/api/v1/mythic-plus/static-data?expansion_id=11` на `raider.io`.

Рейды: ID, имена/slug источника, состав и порядок боссов, source starts/ends. В текущем ответе пять upstream-групп и 20 боссов. Из них 18 боссов явно сопоставлены с пятью рейдами нынешнего каталога. Tier 1 объединяет три разных рейда — отдельная таблица соответствий сохраняет их разделение. Две дополнительные группы/их боссы сохранены как неизвестные для review; по сходству названий они не присоединяются к сайту.

Mythic+: восемь подземелий именно `season-mn-2` / Blizzard season 18, их ID, Challenge Mode ID, исходные названия и таймеры. Глобальный список содержит другое число элементов; несколько сезонов имеют `is_main_season=true`. Адаптер не выбирает сезон по этим неоднозначным признакам. Метаданные остальных сезонов сохраняются для обнаружения нового сезона и review; текущий пул при этом не переключается.

RU-переводы, способности/механики, авторские советы, тактики, маршруты и media этот первый адаптер не обновляет. Они сохраняются отдельно в публичном комплекте первого этапа. Raw API не сообщает точный client build и дату публикации — эти поля остаются неизвестными. Дата source check не становится gameplay verification. Для дальнейшего расширения на Blizzard journal/spells нужны отдельные адаптеры; для Forever — собственный источник и соответствия.

## Хранение и выполнение

Новый пакет `backend/internal/gamecontentcollect` и миграция `00174_game_content_collection.sql` добавляют шесть таблиц: targets, runs, source artifacts, observations, candidates, provider cooldowns. Артефакты и кандидаты неизменяемы. Режим targets ограничен SQL-constraint значением `collect_only`, статус кандидата — `pending_review`.

Исходный JSON сохраняется до нормализации; частичный обязательный состав или неправильная схема записывают неуспешный запуск, сохраняя прежний корректный кандидат. Сетевые ошибки не сохраняют HTML блокировки как успешные данные. Размер ограничен 1 МиБ, HTTP — 25 сек, попытка — 2 мин, один GET на попытку, максимум четыре автоматические попытки. Ошибки содержат безопасный код, без тела ответа или credentials.

Семантический hash не включает дату fetch и порядок JSON-свойств. Неизменное содержимое даёт `no_change`; артефакт переиспользуется. Каждый фактический source check имеет отдельную observation. 304 привязан к сохранённому телу того же запроса/контекста. Diff сравнивается с последним успешно собранным кандидатом; первая загрузка показывает начальное добавление фактов. Это ещё не композиция с опубликованной страницей или редакторское одобрение.

Advisory lock на выделенном соединении разрешает один сбор на контекст/модуль. Повтор после прерывания повышает fence/attempt. Итоговый статус и кандидат атомарны. Повтор завершённого run key обходится без сети. Provider Retry-After хранится в БД и действует на оба модуля, включая новые процессы и суточные задания.

## Расписание и команды

По выбору владельца оба раздела — раз в сутки, отдельная очередь `game_content_collect`, один worker:

- рейды: 03:15 UTC;
- Mythic+: 03:30 UTC.

В Варшаве 22 октября это 05:15/05:30; после перехода на зимнее время — 04:15/04:30. Восстановление после простоя ставит один последний актуальный slot каждого модуля. Сохранившиеся старые задания очереди потребляются без дополнительных запросов; проверены 30 дней для обоих модулей. Manual run остаётся отдельным намерением оператора.

В существующем Go server `GAME_CONTENT_COLLECTION_MODE` по умолчанию `off`; допустим только `collect_only`. При включении регистрируются новые задания и worker, прежние очереди сохраняются. Никакие миграции при старте сервера не выполняются.

Отдельный локальный CLI `game-content-collector`: `init-schema`, `init-queue`, `configure`, `run`, `enqueue`, `worker`, `runs`, `inspect`. Он использует только отдельную loopback-БД `gildra_gc_*`. Публичного HTTP endpoint кандидатов нет; команд approve/publish и опции автопубликации нет.

Реальная PostgreSQL и River использовались только в собственной временной БД. Goose применил 173/174; Down/Up новой миграции сохранили данные публикации первого этапа. Отдельная PostgreSQL-роль без прав UPDATE публикационных таблиц успешно собрала оба кандидата. Fingerprint всех семи таблиц публикации сохранялся; попытка записи через ограниченную роль отвергнута.

Дополнительно проверены: три последовательных полных запуска каждого модуля, idempotency, конкурентный запуск, восстановление прерванной попытки, rollback при ошибке записи кандидата, неизменяемость evidence, возврат к прежним фактам с новым diff, реальная River-доставка, duplicate insertion, startup catch-up и ограничение попыток при snooze.

`live-proof.json` / `live-proof.log`: по три реальных сбора каждого модуля. Два HTTP 200 и четыре HTTP 304; всего два неизменяемых артефакта, шесть observations и два кандидата. Повтор первого ключа не создал новую попытку. Хеши и firstFetchedAt переиспользованных артефактов совпали.
