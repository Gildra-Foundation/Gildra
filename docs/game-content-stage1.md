# Данные рейдов и Mythic+: первый этап

Страницы RU/EN могут читать опубликованный набор данных из Go API во время запроса. Новая публикация и откат не требуют сборки frontend. Импорт пока выполняется локальной командой из существующих проверенных проекций; сборщики источников, расписание, редакторское одобрение и CMS относятся к следующим этапам.

## Модель

- Контекст: `game / edition / channel / region / progressionKind / progressionId`.
- `gc_module_snapshots` — неизменяемое содержимое модуля; `gc_releases` и `gc_release_modules` — согласованный комплект.
- `gc_publication_channels` — активная версия и монотонная `generation`.
- `gc_publication_events` — неизменяемая история: кто, зачем, с каким ключом запроса опубликовал или откатил версию.
- `gc_outbox` — событие в той же транзакции, что указатель и история. Обработчик outbox появится вместе с очередью; сейчас reader проверяет указатель при каждом серверном рендере.

Повтор одного содержимого переиспользует snapshot/release. Публикация требует ожидаемую generation. Два конкурирующих оператора не перезаписывают друг друга. Повтор команды с тем же ключом и теми же аргументами возвращает прежний результат; изменение аргументов с прежним ключом — конфликт. Откат разрешён только к версии из истории публикаций и увеличивает generation.

`retail` и `forever` имеют независимые контексты, версии и каналы. `phase/id` предусмотрен наряду с `season/id`. Для будущей игры можно использовать `raids` и `dungeons`; наличие Mythic+ не предполагается. Нынешние страницы подключают только retail; адаптеры и страницы Forever добавляются отдельно после появления подтверждённых источников и правил игры.

## Локальная проверка

Нужны PostgreSQL 17, Go и зависимости web из lockfile репозитория. Используйте отдельную БД с именем `gildra_gc_*`, доступную через loopback. CLI намеренно не читает `DATABASE_URL` и не принимает удалённую или обычную production-БД.

Из корня рабочей копии:

```sh
cd backend
go build -o /tmp/gildra-game-content ./cmd/game-content
cd ..

# Укажите строку подключения к собственной отдельной локальной тестовой БД.
export GAME_CONTENT_DATABASE_URL='postgres://...@127.0.0.1:15473/gildra_gc_example?sslmode=disable'

/tmp/gildra-game-content init-schema --file backend/migrations/postgres/00173_game_content_releases.sql
node apps/web/scripts/game-content/export.cjs /tmp/gildra-game-content-seed.json
/tmp/gildra-game-content import --file /tmp/gildra-game-content-seed.json
```

Экспорт не обращается в сеть, не пишет в БД и отказывается перезаписывать существующий файл. Он переносит даты, статусы, редакторские заметки и разрешённые публичные проекции. Сырые аудиты и скрытые кандидаты способностей в public manifest не входят. Число боссов переносится отдельным полем с происхождением `existing-published-route-inventory`; это ещё не новый сбор из журнала игры.

Из ответа import возьмите `releaseId`. Импорт создаёт закрытую версию. Для первой публикации:

```sh
/tmp/gildra-game-content publish \
  --release RELEASE_UUID --expected-generation 0 \
  --request-key initial-reviewed-baseline \
  --actor local-operator --reason 'Проверенный начальный набор' --public

/tmp/gildra-game-content serve --listen 127.0.0.1:15474
```

В отдельном терминале запустите web с `GAME_CONTENT_API_URL=http://127.0.0.1:15474`. Переменная нужна серверному процессу и не передаётся браузеру. Сохраните её в окружении последующих сборок и запусков, чтобы маршруты оставались динамическими. Публичный браузер обращается только к Next.js; JSON загружается сервером.

Для последующей публикации используйте актуальную generation из catalog, новый request-key и новую импортированную версию. Для отката:

```sh
/tmp/gildra-game-content rollback \
  --release PREVIOUSLY_PUBLISHED_RELEASE_UUID --expected-generation CURRENT_GENERATION \
  --request-key restore-reviewed-baseline \
  --actor local-operator --reason 'Возврат к проверенной версии' --public
```

Команда без `--public` закрывает весь контекст от публичного API. Это тоже новая generation. Reader очищает ранее публичный кеш при достоверном 404. Ранее публичные версии остаются доступны по UUID, пока сам контекст публичен; черновики и beta/ptr закрыты независимо от знания UUID.

## Чтение

```text
GET /v1/game-content/wow/retail/catalog
GET /v1/game-content/wow/forever/catalog
GET /v1/game-content/releases/{releaseId}/{moduleId}
```

Catalog поддерживает `channel`, `region`, `progressionKind`, `progressionId`; некорректный контекст возвращает 400, непубличный или отсутствующий — 404. ETag поддерживает условное чтение. CDN TTL — 60 секунд; внутренний reader использует `no-store` для указателя и переиспользует неизменяемую проекцию в памяти процесса. Метаданные и страница одного рендера используют одну версию.

При временной ошибке API возвращается последний целиком загруженный набор данного модуля и edition с видимым предупреждением. Если кеша нет, показывается unavailable. Кеш находится в памяти процесса и не переживает его перезапуск. Дата проверки источника при этом не обновляется. Подмена данными другого edition или новой версией указателя со старым содержимым запрещена.

Без `GAME_CONTENT_API_URL` сохраняется прежнее чтение встроенных данных. С настроенным API ошибка не переключает страницу незаметно на встроенный набор.

## Проверки

```sh
node apps/web/scripts/game-content/reader.test.cjs
cd backend
GAME_CONTENT_TEST_DATABASE_URL="$GAME_CONTENT_DATABASE_URL" go test -race ./internal/gamecontent ./cmd/game-content ./cmd/server
```

Интеграционные тесты требуют отдельную локальную БД `gildra_gc_*`, создают собственные случайные схемы и удаляют только их. Без тестовой переменной интеграционные сценарии пропускаются — такой запуск не доказывает работу PostgreSQL.

## Подготовка будущей выкладки

Эта реализация не применяет миграцию при старте сервиса и не меняет production. Миграция `00173` должна пройти штатный Goose-процесс после проверки актуального номера, бэкапа и права на релиз. Read-only handler уже зарегистрирован в Go server. Производственный writer и его авторизация будут отдельной частью интеграции; локальную защиту CLI не обходить заменой строки подключения.

Перед релизом перенесите feature diff на актуальную release-базу, сохраните свежие CMS/аукцион/рейды/M+ изменения, повторите сборку и проверки с включённым runtime reader. Полную старую рабочую ветку поверх сайта не выкатывать.
