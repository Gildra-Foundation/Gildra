# Реализация и приёмка

## Порядок работ

### Этап 0. Базовая версия и источники

Зафиксировать фактические текущие входы страниц, схемы, статусы, coverage и результирующие DTO. Подхватить законченные изменения из параллельных задач по рейдам и Mythic+ после их передачи. Составить таблицу stable entityId ↔ current manifest ID ↔ upstream namespace/ID.

Для каждого набора определить обязательные поля и точный источник. Отдельно выполнить небольшие проверки доступности API/выгрузок, квот, поддерживаемых build и локалей. Уточнить способ использования карт и данных MDT. Ключи источников не запрашиваются через чат.

**Результат:** воспроизводимый начальный снимок и source registry. Текущие черновики остаются черновиками; известные пропуски не объявляются устранёнными.

### Этап 1. Версии, публикация и чтение

Добавить новый Go-компонент gamecontent, миграции `gc_*`, immutable snapshots, active channel generation, публикационный outbox и read-only API. Первым источником служит импорт подтверждённого базового снимка в изолированную БД.

Перевести серверный слой `lib/data` на releaseId с адаптерами нынешних компонентов. Исправить привязки к текущему slug/S2 и вычисление числа боссов из route stops. Сохранить опубликованные URL, локализацию, статусы и granular coverage.

**Результат:** изменение тестового опубликованного снимка видно на существующих страницах без новой frontend-сборки. При откате возвращается согласованный прежний набор.

### Этап 2. Сбор и retail-модули

Подключить SourceArtifact, fetch limits, job idempotency и оркестрацию River. Внедрить `retail.raids` и `retail.mythic-plus`, начав с идентичностей, состава и таймеров. Существующие аудиты журнала/способностей/медиа запускать с изолированными артефактами и параметрами, без записи в общие TS-файлы.

Включить `collect_only`. Проверить как минимум три последовательных полных запуска с повтором того же содержимого и контролируемыми ошибками. Это предложение начального критерия, не доказательство достаточности всех будущих изменений.

**Результат:** каждый запуск даёт объяснимый diff, покрытие и состояние источника; действующие страницы читают только одобренную версию.

### Этап 3. Редакторский слой и админка

Добавить staff bridge, роли, просмотр кандидатов, закрытый RU/EN preview, одобрение, отклонение, паузу и откат. Перенести ручные пояснения и тактики в версионированный слой. Связать маршруты с map/difficulty/spell dependencies.

**Результат:** ручные правки переживают импорт; изменение механики отмечает затронутые блоки и не создаёт ложное подтверждение прохождения в игре.

### Этап 4. Ограниченная автопубликация

На стенде прогнать перечисленные ниже сценарии. Зафиксировать политику источников и пороги. Включать автоматические поля по одному модулю, сохраняя структурные и редакторские изменения для просмотра. Добавить сводку ошибок, давности, затрат и восстановления кеша.

**Результат:** поддерживаемые факты обновляются по расписанию без оператора; ошибки оставляют последнюю корректную публикацию и объяснимую задачу в админке.

### Этап 5. Forever

Уточнить реальные источники, модель прогрессии и возможности игры. Зарегистрировать `edition=forever`, независимые источники и `forever.raids`/`forever.dungeons`; поддержка beta/live проверяется отдельно. Подключить будущий сайт к своему публикационному каналу. При наличии подтверждённой системы Mythic+ добавить её собственный модуль.

**Результат:** второй сайт использует общую инфраструктуру обновления и свои данные; совпадение названий/ID с retail не смешивает содержимое.

## Предлагаемые изменения в коде

Пути ниже — план, создавать их в текущей работе не требовалось.

```text
backend/internal/gamecontent/
  contexts/           # контекст, идентичности, схемы и реестр модулей
  modules/raids/       # правила рейдов и проекции
  modules/mythicplus/  # правила подземелий и проекции
  publication/        # версии, кандидаты, CAS, outbox, откат
  editorial/          # версии ручных данных и зависимости
  delivery/           # public read API и внутренние команды
backend/internal/datasetrefresh/  # подключение новых River jobs
backend/migrations/postgres/      # новые миграции gc_*, без правок старых
scraper/sources/                  # адаптеры и сохранение SourceArtifact
apps/web/lib/data/                # runtime reader и совместимые DTO
apps/web/components/wow/raid/     # переход с compiled data на props
apps/web/components/wow/mythic/   # отделение фактов от маршрута
cms/...                          # раздел «Данные игры» в актуальном CMS checkout
```

Расположение существующих пакетов и CMS уточняется перед кодированием. Изменения frontend/data из текущих параллельных работ сначала сверяются с их handoff и блокировками.

## Сценарии тестирования модулей

Это спецификация будущих проверок. Во время проектирования они не запускались.

| ID | Модуль / сценарий | Ожидаемый результат |
|---|---|---|
| S01 | Источник возвращает 304 и есть сохранённое тело | Используется точный прежний artifact; не возникает новая семантическая версия или новая дата gameplay verification |
| S02 | 304 без тела либо для другой локали/сборки | Явная ошибка или полный повторный запрос; проверки не объявлены пройденными |
| S03 | Вместо JSON получен HTML ошибки с HTTP 200 | Запуск failed; active release не меняется |
| S04 | Превышены лимит страниц/объёма/бюджета или rate limit | Сбор ограничивается; осмысленный retry только для временной ошибки; частичный набор не публикуется |
| S05 | Неверный build или namespace при валидной схеме | Вход отклонён по контексту |
| S06 | Повторная нормализация тех же артефактов | Совпадают содержимое, порядок, семантический хеш и coverage |
| D01 | Одинаковый spell/NPC ID в retail и Forever | Разные сущности/версии; связи между edition не возникают |
| D02 | Название изменилось, upstream identity прежняя | Стабильный entityId и URL; diff содержит поле имени |
| D03 | Название совпадает у двух NPC | Неоднозначность не разрешается выбором первого совпадения |
| D04 | Журнал содержит цикл или отсутствующую дочернюю секцию | Проверка дерева завершается с нарушением; блок не объявлен полным |
| D05 | Разные значения способности на двух сложностях | Сохраняются правильные варианты с точным difficulty, без общего выдуманного значения |
| D06 | Описание содержит `$...` или неразобранный токен | Текст удержан; виден пропуск покрытия и причина |
| D07 | Имя NPC подтверждено, портрет неизвестен | Identity verified, portrait missing; допустимый placeholder без чужой модели |
| D08 | Источник потерял одного босса из-за частичного ответа | Автоматического удаления нет; опубликованная версия сохранена |
| D09 | Источники таймера расходятся | Candidate conflict/review_required, не «последний ответ победил» |
| D10 | Таймер изменён в разрешённых пределах и с нужным подтверждением | Новая публикация факта; связанные расчёты обновлены, маршрут получает точечную задачу сверки |
| D11 | Новый raid/season или новая связь spell/encounter | Структурное изменение ожидает просмотра, даже если JSON валиден |
| D12 | Неполное описание необязательной способности | Явный статус/coverage; публикация возможна только если предметный контракт разрешает этот пропуск |
| D13 | Retail-сезон сменился | Архивные страницы остаются доступны; текущий сезон выбран из данных, без React-правок |
| D14 | Forever не заявляет таймеры/forces | UI не рисует несуществующие значения, модуль подземелий продолжает работать |
| D15 | Карта и координаты пришли из разных MDT commits | Несовместимый маршрут не выводится как точный |
| D16 | Расчёт forces с пропуском/дубликатом clone | Не получается ложное «100%»; проверяются набор clone и total forces конкретной версии |
| D17 | Официальный hotfix новее выгрузки клиента | Старая таблица не отменяет изменение; конфликт и влияние на тактику сохранены |
| J01 | Два worker одновременно берут один slot | Только один активный run; повтор возвращает тот же runId |
| J02 | Шесть почасовых slot в один день | Шесть разных idempotency keys; дневная дата не подавляет пять запусков |
| J03 | Worker умер после fetch | Повтор использует сохранённый вход либо безопасно собирает заново; double publish отсутствует |
| J04 | Истёк lease старого worker | Его fencing token не даёт изменить опубликованный канал |
| J05 | Сервис возобновился после суток простоя | Создаётся актуальный catch-up, без неконтролируемого всплеска fetch |
| P01 | Crash до commit публикации | Старый active release и все его связи прежние |
| P02 | Crash после commit до инвалидирования кеша | Outbox повторяется; читается новый release не позже TTL указателя в штатном режиме |
| P03 | Одобрен кандидат, затем изменилась редакторская версия | Старое одобрение не действует; diff пересчитывается |
| P04 | Пока кандидат ждал, опубликован другой release | CAS 409; повторная оценка относительно актуальной generation |
| P05 | Откат и завершение старого refresh совпали | Откат имеет новую generation, старый refresh не отменяет его |
| P06 | Обновление M+ не меняет рейды | Новый manifest содержит новый M+ snapshot и прежний совместимый raid snapshot |
| P07 | Меняется общая зависимость двух модулей | Публикуется совместимый комплект либо пакет удерживается |
| P08 | Двойная команда approve с Idempotency-Key | Один publication event и тот же результат |
| P09 | Очистка истории пытается удалить active/referenced snapshot | Удаление запрещено ссылками и правилами retention |
| E01 | Редактор исправил текст, потом прошёл импорт | Правка и авторство сохранены; обновлён базовый факт/конфликт |
| E02 | Изменилась механика, используемая в трёх тактиках | Эти три блока получают needs_review; независимые не теряют статус |
| E03 | Источник проверен сегодня, маршрут не проходили в игре | Дата gameplay verification прежняя/null |
| E04 | Обновлён spell, на который назначен игрок в workspace | Личное назначение не перезаписано; несовместимость видна пользователю |
| E05 | Staff сайта A запрашивает кандидат закрытого канала B | Отказ, включая прямой запрос preview по UUID |
| E06 | Подделан actorId в запросе | Команда не выполняется без серверной аутентификации и проверки роли |
| W01 | Каталог и boss page запрашиваются во время переключения версии | Каждый запрос использует согласованный release; внутренние ссылки разрешаются в нём |
| W02 | RU-факт отсутствует, EN присутствует | Явный допустимый fallback/неполнота, без смешанной локализации и ложного verified |
| W03 | Public API запрашивает beta/draft releaseId | Доступ закрыт независимо от знания UUID |
| W04 | API недоступен, есть совместимый кеш | Показывается опубликованный кеш с честной давностью |
| W05 | API недоступен и кеш отсутствует | Понятное unavailable; данных другого сезона/edition не появляется |
| W06 | Новый snapshot опубликован без frontend build | Каталог, вложенные страницы и счётчики обновляются в пределах целевого TTL |
| W07 | Переименован slug после одобрения | Старый URL перенаправляет на стабильную сущность; sitemap обновлён |

## Проверки по уровням

**Unit:** нормализация, identity mapping, вычисление diff, источники полей, политика, разрешение зависимостей и состояния тактики.

**Контракт:** закреплённые небольшие ответы каждого поставщика, корректные/неполные/изменившие схему ответы, module snapshot schema, совместимость public DTO и version negotiation. Выгрузки с ошибками служат отрицательными fixtures, не публичной статистикой.

**Интеграция с временной PostgreSQL:** ограничения gc_*, CAS, параллельная публикация/откат, транзакционный outbox, идемпотентность, отсутствующие внешние связи. Никаких тестовых записей в production.

**Browser на стенде:** RU/EN, каталог и вложенные страницы, 320/390/768/1440 px, loading/empty/error, источники и даты, смена версии без новой сборки, закрытый preview и права staff, отсутствие утечек raw/credentials в HTML.

## Критерии готовности первой версии

- Два retail-модуля обновляются по расписанию и вручную через очередь.
- У каждого опубликованного факта есть точный контекст и достаточное доказательство либо явно обозначенный неполный статус.
- Невалидный/частичный источник не заменяет корректную публичную версию.
- Просмотр кандидата показывает разницу и влияние на тактику; ручные правки переживают импорт.
- Публикация и откат атомарны, повторяемы и проверены при конкуренции.
- Новые данные видны без пересборки сайта; RU/EN и старые URL сохранены.
- Forever подключается новым предметным модулем и настройкой канала; тест изоляции edition проходит.

Срок реализации оценивается после этапа 0: основные неизвестные — качество источников, разбор существующего контента и схема авторизации CMS. Срок запуска игры не заменяет эту оценку.
