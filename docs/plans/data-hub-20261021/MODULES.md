# Модули и зоны ответственности

## A. Источники и сбор

**Назначение:** получить воспроизводимый исходный снимок без участия посетителя сайта.

**Внутри модуля:** аутентификация поставщика, rate limits, HTTP retries/304, формат ответа, раскладка DB2/JSON/страницы, закрепление commit/build. Типовые адаптеры: `blizzard-news`, `blizzard-game-data`, `client-tables`, `raiderio-static`, `mdt`.

**Классификация:** обслуживающая область — обеспечивает данные продукту. При этом форматы поставщиков меняются часто, поэтому требуют собственной границы.

**Контракты:** принимает FetchPlan от предметного модуля через orchestrator; возвращает SourceArtifact и decode report. Не знает JSX, URL страниц Gildra, правил редакторского одобрения и active release.

**Одиночные изменения:** новый формат Raider.IO затрагивает только его адаптер; новый источник таймеров требует адаптера и явного изменения политики соответствующего модуля.

**Переиспользование:** действующий Python scraper worker и инфраструктура профилей/бюджетов. Существующие JS-аудиторы сначала используются как закреплённые инструменты с изолированными входом и выходом. Их режимы `--write` не запускаются против общих исходников или production-каталогов.

## B. Предметный контент retail и Forever

**Назначение:** превратить источник в корректные игровые факты и готовые данные раздела.

**Внутри модуля:** контекст edition/build, словарь идентичностей, связи encounter/NPC/spell, состав контента, сложности, проверка текста, точные правила полноты, расчёт diff и влияния на пояснения.

**Классификация:** основная изменчивая область — определяет полезность и достоверность разделов Gildra. Нормализация, валидация и построение публичной проекции работают рядом и используют одну модель.

**Начальный набор:**

| moduleId | Данные | Возможности |
|---|---|---|
| `retail.raids` | Каталог, encounter journal, версии способностей и доказательства | journal, difficultyVariants, roleGuidance |
| `retail.mythic-plus` | Состав сезона, таймеры, dungeon journal, maps, модели NPC/forces | timers, maps, routes, enemyForces — только при доказанном покрытии |
| `forever.raids` | Каталог и журнал именно Forever | По фактическим источникам и модели сложности Forever |
| `forever.dungeons` | Подземелья именно Forever | Набор подтверждённых возможностей; таймеры/forces не обязательны |
| `forever.mythic-plus` | Регистрируется только после подтверждения системы | Отдельные источники и правила |

**Общее:** чистые библиотеки идентичности, provenance, локалей и журналов. Retail-specific правила не наследуются Forever молча. Модуль может переиспользовать совместимый алгоритм, но обязан объявить свою поддержку источника и контекста.

**Контракты:** ModuleDescriptor, ArtifactPlan, DomainCandidate, ValidationReport, ChangeSet, ImpactReport, PublicProjection. Все определены в [CONTRACTS.md](CONTRACTS.md).

**Одиночные изменения:** новый retail-сезон меняет реестр контекста и данные; новый способ прогрессии Forever меняет его модуль; новый босс в поддерживаемой модели становится данными после проверки. Новая неизвестная механика интерфейса может потребовать доработки модуля и renderer.

## C. Расписание и оркестрация

**Назначение:** гарантировать исполнение и повторение заданий с контролируемой нагрузкой.

**Внутри модуля:** точное scheduledFor, runKey, дедупликация, lease, fencing token, пауза, backoff с jitter, ограничения источников, recovery после crash.

**Классификация:** типовая обслуживающая функция. Используется существующая очередь River и PostgreSQL.

**Контракты:** команды refresh/pause от staff и расписания; планы от module registry; события run_finished и candidate_ready. Ошибка внешнего сервиса не становится синхронной ошибкой пользовательской страницы.

**Поведение:** максимум один активный обновляющий запуск на moduleContextKey, ограниченное число fetch на поставщика. Ручной повтор получает requestId; автоматическое расписание — UTC slot, включающий часы и минуты. Временная ошибка повторяется; неверная схема или неоднозначный ID ожидают исправления, а не бесконечного повтора.

**Одиночные изменения:** новая периодичность или бюджет не требуют изменения модели рейда и frontend. При возобновлении выбирается один актуальный пропущенный slot вместо шквала всех накопленных запусков.

## D. Издатель и версии

**Назначение:** единолично владеть опубликованным состоянием и правом его изменять.

**Внутри модуля:** immutable snapshots, release manifest, policy/approval hash, CAS generation, совместимость зависимостей, атомарная публикация, откат, audit и outbox.

**Классификация:** обслуживающая область с сильными локальными транзакционными связями. История, указатель и outbox находятся в одной БД и одном компоненте.

**Контракты:** получает валидированный кандидат, политику и подтверждённого актора. Возвращает releaseId/generation либо объяснимый отказ. Предметный модуль не выдаёт себе права публикации.

**Одиночные изменения:** изменение срока хранения и способа доставки cache event не меняет парсер. Добавление нового вида контента не меняет алгоритм переключения release при совместимой схеме.

## E. Редакторские данные и рабочее место

**Назначение:** показывать изменение и сохранять решения человека без перезаписи очередным импортом.

**Внутри модуля:** версии авторских текстов, статус проверки тактики, зависимости от игровых фактов, просмотр diff, причина ручной корректировки. UI располагается в существующей CMS, операционные данные принадлежат gamecontent.

**Классификация:** авторские тактики и качество — основная область продукта. CRUD кандидатов, роли и история — обслуживающие части. Они не должны заставлять переносить игровые правила в формы CMS.

**Контракты:** UI получает preview/diff DTO, отправляет команды с ожидаемой generation и хешем. CMS server выполняет авторизованный bridge в Go; Go самостоятельно проверяет разрешённую область. Изменение редакторской версии создаёт новый кандидат.

**Одиночные изменения:** новый вид карточки проверки не меняет сборщик. Замена оболочки CMS сохраняет команды и семантику публикации.

**Предпросмотр:** закрытый кандидат, RU/EN, источник каждого изменения и список затронутых страниц. Предпросмотр не меняет public currentRelease, sitemap и public cache.

## F. Чтение и страницы

**Назначение:** быстро показать одну согласованную опубликованную версию на каталоге и вложенных страницах.

**Внутри модуля:** public DTO, разрешённые каналы, release pinning, cache key, ETag, локализованные состояния, стабильные URL и SEO.

**Классификация:** обслуживающий delivery-компонент. Продуктовые требования к чтению должны быть выражены в DTO, не через доступ frontend к таблицам.

**Контракты:** Go отдаёт ограниченную проекцию; `apps/web/lib/data` читает её на сервере. Компоненты получают только необходимые данные. Политики качества и вычисление игрового статуса не дублируются в браузере.

**Одиночные изменения:** новая компоновка списка рейдов меняет UI. Новый сезон в поддерживаемой модели не требует React-правок. Другой сайт Forever использует свою конфигурацию канала и общие компоненты там, где совпадают возможности.

## Подключение следующего модуля

1. Заявить edition/channel, предметную схему, capabilities, источники и зависимости.
2. Реализовать недостающие адаптеры и module normalize/validate/project.
3. Подготовить fixture исходного ответа и контрактные сценарии.
4. Зарегистрировать модуль и расписание в режиме `collect_only`.
5. На стенде проверить изоляцию edition, неполные источники и публичную проекцию.
6. Подключить сайт к нужному publication channel и включить политику после приёмки.

Новый исполняемый модуль один раз проходит обычный выпуск кода. Последующие данные внутри его возможностей обновляются через Data Hub. Из произвольной загруженной ZIP-папки или URL сервер не запускает код.
