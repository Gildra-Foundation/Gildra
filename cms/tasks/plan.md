# План завершения общей админки Gildra / Riftden

Дата: 2026-10-19. Область: CMS на https://cms.gildra.net и её связи с двумя сайтами.
Задачи и критерии: [todo.md](todo.md). План каталога WoW в корневом `tasks/` — отдельная работа.

## Что считаем готовой админкой

Редактор входит, создаёт материал для выбранного сайта, пишет RU/EN, проверяет его
в оформлении сайта, передаёт на публикацию и видит правильную публичную версию.
Администратор управляет только разрешёнными сотрудниками и читателями. Действуют
восстановление доступа, статистика, журнал действий и проверяемое восстановление
из резервной копии. Для всех функций явно показаны недоступность и ошибки.

## Проверенные исходные факты

- Новые экраны Valyro: пульт, статьи, пользователи, аналитика, выбор сайта.
- Нативный Payload-редактор: версии, автосохранение черновиков, публикация,
  RU/EN и сверка перевода. Права owner/admin/editor/author/analyst уже реализованы.
- В production до этого релиза: `gildra-cms:cms-ux-20261013`, отдельный jobs worker;
  все четыре миграции применены, новых миграций в текущем изменении нет.
- На 2026-10-19 08:19 UTC: почта `disabled`, регистрация обоих сайтов выключена,
  `CMS_READERS_ENABLED` не задан у обоих фронтендов. В CMS один сотрудник и нет читателей.
- Plausible CE работает; URL и ключ заданы в CMS, домены заданы в sites,
  переменные скрипта заданы на обоих фронтендах. Это ещё не доказывает сбор и
  корректность отчётов: требуется сквозная проверка, а не повторная установка.
- Подписи обновления кеша и адреса receivers настроены для обоих сайтов.
  Их реальное поведение после публикации требуется проверить.
- Локальный CMS preview и выбор внешнего preview реализованы. Корректность внешнего
  preview в текущих фронтендах пока не подтверждена.
- Статус публикации общий для RU/EN. Go/Battle.net и CMS имеют отдельные учётные
  записи. Не объединять их по совпавшему email.

## Порядок работ

| Приоритет | Задачи | Результат |
|---|---|---|
| P0 | 1. Релиз и регрессионная приёмка | Новая версия работает, данные сохранены, откат подготовлен |
| P0 | 2. Доставка почты и восстановление доступа | Проверенные письма и рабочий сброс пароля сотрудника |
| P0 | 3. Публикация и снятие на двух сайтах | Изменения появляются, снятое и чужие черновики не доступны |
| P0 | 4. Проверка ролей и границ сайтов | Автор не публикует; сотрудник не получает чужой сайт |
| P1 | 5. Предпросмотр в оформлении сайта | Черновик виден по ограниченной ссылке только сотруднику |
| P1 | 6. Понятная работа RU/EN | Видны заполненность, fallback и общий статус публикации |
| P1 | 7. Аналитика реального трафика | Один визит проходит от сайта до соответствующего отчёта |
| P1 | 8. Читательские аккаунты | Регистрация/подтверждение/вход/сброс/блокировка на обоих сайтах |
| P1 | 9. Резервные копии, jobs и наблюдение | Восстановление проверено; сбой не остаётся незамеченным |
| P2 | 10. Финальная UX-приёмка и инструкция | RU/EN, телефон, клавиатура и рабочие сценарии приняты |

Сначала закрыть P0. После этого редакция может работать со статьями. Открывать
регистрацию читателей только после задач 2, 4, 8 и проверки восстановления (9).
Работы 5–7 можно вести независимо после P0; задача 10 завершает приёмку.
Оценка порядка величины: 7–12 рабочих дней одного инженера с проверками;
настройка DNS/PTR/почтового провайдера может добавить внешнее ожидание. После
задачи 1 уточнить оценки по фактическим дефектам, а не считать эту оценку сроком.

## Решения и границы

- Сохранить Payload для входа и редактора; Valyro использовать на рабочих экранах.
- Сначала подтвердить уже реализованные функции и устранить конкретные дефекты.
- Сохранить общий статус RU/EN, явно объяснив его в UI. Независимая публикация
  языков — отдельная будущая задача с миграцией и решением владельца.
- Не подключать Go/Battle.net identities к CMS автоматически. Если нужен единый
  кабинет, сначала согласовать связывание по подтверждённому входу у провайдера,
  отзыв доступа и границы данных; это отдельный проект, не условие редакционной готовности.
- Почтовые, аналитические и reader-настройки не включать в текущий релиз интерфейса.
  Следующие production-изменения выполняются в рамках соответствующих задач.
- Коммиты и push — только по отдельному запросу. Для текущего релиза сохранить
  неизменяемый снимок исходников, SHA-256 manifest, image ID, backup и команду отката.

## Выпуск и проверки

Текущий релиз: сборка Docker runner и jobs из одного снимка, тесты на изолированном
PostgreSQL, браузерные сценарии, резервная копия с восстановлением в изолированный
PostgreSQL, затем блокировка `prod:production` и обновление только CMS/jobs.
После обновления: health, новая форма входа, статические файлы, защита API,
неизменность опубликованного публичного контента и контроль журналов.

Результат и точные артефакты выпуска фиксируются в
`/home/debian/gildra-cms-release-20261019/RELEASE.md` после проверки; состояние
задачи 1 в todo обновляется только по фактическому исходу публикации.

## Риски

- Параллельный релиз web: дождаться освобождения общей production-блокировки;
  перечитать release env и менять только CMS_IMAGE/CMS_JOBS_IMAGE.
  В будущем сборку и staging QA выполнять до взятия production-lock; держать
  общую блокировку только на переключении, проверке и возможном откате.
- Недоставленные письма: сначала проверить DNS/relay и доставку, затем включать
  SMTP и регистрацию; не маскировать проблему успешным уведомлением.
- Черновик изменяет публичную ссылку: проверять опубликованный slug и перевод.
- Ошибки revalidation: проверять публикацию, изменение slug и снятие с публикации;
  отдельный worker, видимые отказы и повторные попытки.
- Резервная копия без восстановления: проверять на отдельной БД, сохранять вне
  сервера по выбранной политике хранения; не считать наличие dump доказательством.
